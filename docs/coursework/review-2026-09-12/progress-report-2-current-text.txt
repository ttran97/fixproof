FixProof: A Validation-Oriented System for AI-Generated Vulnerability Remediation

Tony Tran

Progress Report 2 - Current verified update, September 12, 2026

Problem Statement:

AI coding tools can create insecure code, and a proposed security repair can leave the vulnerability exploitable or modify intended application behavior. Disappearance of a static-analysis warning therefore gives incomplete evidence of a correct repair. Pearce et al. (2021a) found approximately 40% of 1,689 Copilot-generated programs vulnerable in their selected security scenarios. Research on vulnerability repair and validation feedback already exists (Pearce et al., 2021b; Kulsum et al., 2024). FixProof investigates how separate validation evidence can support a human patch decision in a small, controlled JavaScript/Express setting, without claiming to be the first system to confirm generated repairs.

Solution Statement:

FixProof is a Python prototype that scans controlled JavaScript/Node.js Express applications with Semgrep CE, normalizes findings, and supplies a remediation model with one finding and focused source context. It applies the returned candidate to a copied workspace, then performs JavaScript syntax checks, SAST comparison, targeted security tests, and functional tests. Deterministic Python policy produces REJECT, READY_FOR_HUMAN_REVIEW, or NEEDS_HUMAN_ADJUDICATION. The model generates replacement source code; it does not author the evaluation tests at runtime, grade its own patch, or record human approval. Deliverables are the prototype, three versioned CWE benchmarks, auditable evaluation artifacts, an evidence dashboard and CLI demonstration, documentation, and the final report/presentation.

In response to the professor's scope feedback, the evaluated applications are deliberately constructed fixtures for reflected XSS (CWE-79), SQL injection (CWE-89), and path traversal (CWE-22). Each has a fixed route, attacker-controlled input, vulnerable sink, synthetic data, and expected benign behavior. AI generates the repair candidates. This narrows the original proposal: the primary study evaluates repairs of controlled fixtures, not a representative corpus of AI-generated web applications.

Questions I have or Issues I’m running into:

The main observed methodological issue is disagreement: ten primary candidates pass targeted runtime and functional checks while their SAST target persists. All ten conflicts now have human reviews: seven candidates were accepted within the controlled route scope and three requested additional testing. The requests identify concrete evidence gaps rather than treating either SAST persistence or fixed-test success as conclusive. The brief XSS 01, 02, and 05 rationales still need a dated explanatory supplement.

The primary sample contains no SAST false successes, so it cannot establish a detection rate for naturally generated patches that clear SAST but fail later checks. One app per CWE and identical SQLi source across five calls also limit diversity. Remote Semgrep auto rules were not fully archived, and the fresh-environment check used the same Windows host. These are limitations to report, not reasons to revise completed observations.

Is the refined three-fixture scope with repeated repairs and a separate supplemental test set sufficient to address the original scope concern? Would a second reviewer for selected disagreements be a more useful extension than another vulnerability class? 

Methodology Paragraph Summary:

Each primary fixture defines a target route, attacker-controlled input, vulnerable operation, synthetic data, and expected benign behavior. Baseline security checks establish the intended vulnerability independently of scanner detection. The frozen study uses Semgrep 1.136.0, a disclosed controlled SQLi rule where default coverage missed the target, and gpt-5.2 for five separate initial calls per CWE. Prompts withhold evaluator ground truth and test implementations. The model returns structured repair fields; implemented validators execute HTTP security/functional checks, with Chromium execution observations for primary XSS. SAST-only interpretation and the full deterministic policy are compared on the same saved candidate. Initial attempts, pilot retries, non-AI controls, human conclusions, and post-collection lifecycle work are analyzed separately. Repeated calls on one fixture are not independent applications, and passing targeted tests does not prove application-wide security.

Background research informs the design rather than merely motivating the topic. Pearce et al. (2021a) motivates testing generated code under explicit security scenarios; Pearce et al. (2021b) reports challenges with functionally correct vulnerability repairs, motivating separate benign-behavior checks. Kulsum et al. (2024) uses external patch-validation feedback in VRpilot, providing precedent for a bounded feedback retry. FixProof's narrower contribution is its auditable combination of scanner, runtime, functional, and human-decision evidence; it does not establish superiority over those systems. Semgrep's documentation supports explicitly configured default and local rules. OWASP WSTG v4.2 informs the planned supplemental testing, but the implemented suite is not complete WSTG coverage.

Target-SAST resolution is 33.3%; SAST/runtime disagreement is 66.7%. No primary SAST false success or new SAST finding was observed. The 15 response IDs produced 11 distinct candidate sources: five XSS, one SQLi, and five traversal. Human conflict-review completion is 10/10 (100%): seven accepts within the controlled route scope and three requests for additional testing. The five SQLi readiness decisions are not recorded approvals. Each XSS candidate has four attack checks and six functional checks; each SQLi and traversal candidate has one attack plus one benign security control, and three functional checks. Consequently, a 15/15 pass rate is an attempt-level result, not coverage of 15 independent applications or all input variants.

The separate pilot demonstrates a functional regression: the first XSS patch changed legitimate text into output containing 'undefined' and failed two of six functional checks. Its retry passed those checks while SAST persisted. This is not a SAST false success. The separately constructed non-AI static-output control clears the target SAST warning but fails all six functional checks, with security validation inconclusive; FixProof rejects it. This demonstrates rejection of a misleading SAST success caused by removing intended behavior, not an observed AI patch that clears SAST while retaining an exploitable vulnerability. No initial primary candidate was rejected, so primary retry improvement is not applicable.
