Why the SAST warning may persist: >- Both CWE-79 rules now point to candidate line 17, where res.send receives "<h1>Hello " + escapeHtml(name) + "</h1>". One rule conservatively detects user data in manually constructed HTML, and the other detects user input written directly to a response. It also detects execution primarily through alert dialogs. An optional stronger supplemental test would exercise those values and assert that the resulting h1 contains only one text node, has no attacker-created child elements, and displays the original input exactly. A property/fuzz test over arbitrary strings would provide broader assurance. This uncertainty does not reveal a concrete bypass in the present sink, because the implementation encodes ampersands before encoding every < delimiter. Proposed verdict and justification: >- ACCEPT_CANDIDATE within the controlled /hello-route scope. The patch applies correct HTML element-content encoding before the only response sink, preserves the route's intended visible greeting for the tested normal and special inputs, introduces no new SAST findings, and retains the original missing-name coercion behavior. The persistent scanner finding is best explained by lack of recognition of the local escaping helper. Acceptance would not imply that the helper is safe if its output is later reused in an attribute, URL, JavaScript, CSS, or another context.
